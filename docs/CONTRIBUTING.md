# Contribute a plugin

Submit a pull request to `jordanmeyer/decision-999`. The initial collection has one real example; only add listings for working packages you include and test.

Create `plugins/<machine-name>/plugin.json` using the portable Agent Plugins schema, with a unique lowercase hyphenated name, version, and accurate description. Put complete skills under `skills/<skill-name>/SKILL.md`, retaining resources, notices and provenance. Include a package README with prerequisites, installation, actual invocation, representative task, tested output and limitations. Keep paths relative to the installed package; write generated artifacts into the user's project. Do not commit credentials, personal configuration, caches or generated builds.

Add the package to `.agents/plugins/marketplace.json` with a repository-root-relative `./plugins/<machine-name>` path, local source, available installation policy and on-install authentication policy. Use the current existing entry as the shape. Add a same-key record in `site/presentation.json` with a unique slug, title, summary, description, capabilities, inputs, outputs, sample task, and instructions URL. The instructions URL must lead to a real neutral anchor in the root README. Add that README section linking to your package instructions. Versions come from the manifest; do not duplicate them in the website metadata.

Website fields must be neutral and accurate. The website must never contain `duke` in any case, including link URLs, metadata, code, filenames or hidden text. No institutional or invented logos, seals, mascots, marks or favicons are allowed. Do not copy raw plugin metadata/assets to the site. Keep the independent-demonstration identity and do not invent adoption counts, endorsements, reviews or affiliations.

Run `python3 scripts/build.py` and `python3 scripts/check.py`. Preview under `/decision-999/` with `python3 scripts/serve.py`, inspect narrow/desktop layout, and test keyboard navigation, copy success/failure and links. A catalog entry plus its presentation record automatically produces its card and detail section; page code should not need editing.

Test local installation with a fresh temporary Codex state directory and external working directory, then test the published Git source in a separate clean state directory after merge. The documented `CODEX_HOME` environment override isolates config/cache; its directory must already exist. Do not share local registrations or caches with the published test and do not change the normal user configuration. Inspect marketplace and plugin JSON listings to verify the source, then invoke the skill in a new session and confirm resource reads use the installed path. Do not rename or alter another source project to force this test.

In the pull request, describe the purpose, supported inputs/outputs, required tools, provenance/rights, exact tests, actual results, and known limitations. For updates, bump the package version and explain material portability changes. Maintainers should review installed-package behavior and neutral rendered output before merging. Deployments are limited to `main` and wait on validation.
